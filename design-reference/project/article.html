Killing cold starts: how I cut Lambda latency by 70%

td thedev May 28, 2026 8 min read 1,240 words
#aws #lambda #performance

Provisioned concurrency is the answer everyone reaches for first. It's also a way to spend a lot of money papering over a problem you haven't measured yet. Here's the order I'd actually attack cold starts in — cheapest, highest-leverage fixes first.

Late last year our p99 on a customer-facing checkout API drifted past 2.8 seconds. Not the median — the median was fine — but enough requests were hitting cold Lambdas that support tickets started rolling in. We had ~40 functions behind an API Gateway, most of them Node, a couple in Python. This is the playbook we used to claw most of that latency back without throwing money at provisioned concurrency.

Rule of thumb: measure first, then optimize the thing the data points at. Cold starts feel like one problem but they're usually three or four stacked on top of each other.

Measure before you touch anything

A "cold start" is really two numbers: the time AWS spends initializing your execution environment, and the time your init code spends before the handler is ready. CloudWatch gives you both if you know where to look. The Init Duration field in the REPORT log line is the one that matters.

Pull a week of init durations and bucket them. We were surprised: the AWS-managed portion was stable at ~180ms, but our own init was wildly variable — some functions spent over a second loading SDK clients and parsing config they didn't need yet.

cloudwatch-insights.sql 
-- Worst cold starts in the last 7 days
filter @type = "REPORT"
| fields @initDuration, @duration, @requestId
| filter ispresent(@initDuration)
| sort @initDuration desc
| limit 25
TipIf you only do one thing from this post, do this query. We found two functions that accounted for 60% of the bad tail purely from a misconfigured logging library loading at import time.

Shrink the package, shrink the start

Init time scales roughly with how much code the runtime has to load and parse. The single biggest win for our Node functions was getting honest about the bundle.

Bundle and tree-shake

Shipping node_modules raw is the default and it's almost always wrong. We moved to esbuild and cut one function's deployment artifact from 14 MB to 380 KB. Init dropped from 900ms to under 200ms.

build.mjs 
import { build } from "esbuild";

await build({
  entryPoints: ["src/handler.ts"],
  bundle: true,
  minify: true,
  platform: "node",
  target: "node20",
  // the AWS SDK is on the runtime already — don't ship it
  external: ["@aws-sdk/*"],
  outfile: "dist/handler.js",
});

Lazy-load the expensive stuff

Anything you import at the top of the file runs during init, whether the handler needs it or not. Move heavy clients behind a function so they initialize on first use and get reused across warm invocations.

handler.ts 
let _db: Pool | undefined;

// created once per warm container, not on every cold start
function db() {
  if (!_db) _db = new Pool({ max: 1 });
  return _db;
}

export const handler = async (event) => {
  const rows = await db().query("select 1");
  return { statusCode: 200, body: JSON.stringify(rows) };
};

Pick the runtime on purpose

Runtimes are not equal at cold start. In our testing, on identical workloads, the rough ranking from fastest to slowest init was: compiled binaries (Rust / Go via the custom runtime) → Node → Python → JVM. If a function is on a hot path and does little more than shuffle JSON, a tiny Go binary starts in single-digit milliseconds.

We didn't rewrite everything — that would be its own kind of expensive mistake. We rewrote the two worst offenders and left the rest. Choosing boring architecture applies here too: only move what the data tells you to.

Watch outARM (Graviton) is cheaper and often faster, but double-check any native dependencies actually have arm64 builds before you flip the architecture flag.

When provisioned concurrency is actually right

After all of the above, our p99 was down to ~850ms and the tickets stopped. For the one endpoint with a hard sub-300ms SLA, we finally turned on provisioned concurrency — but only for that function, scaled on a schedule around peak traffic. Reaching for it last meant we paid for a fraction of what we'd have provisioned if we'd started there.

  • Measure the init breakdown before changing anything.
  • Bundle and tree-shake — usually the biggest single win.
  • Lazy-load heavy clients out of the init path.
  • Right-size the runtime for hot paths only.
  • Provision last, narrowly, and on a schedule.

The whole effort took about a week of focused work and the AWS bill went down, because smaller packages and shorter durations cost less. The lazy answer would have cost more and fixed less.
